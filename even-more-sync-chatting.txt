⏺ Here's how I read your intent, and a thorough plan to fill it out:

  ---
  What you're getting at

  The core insight is that flopy4.mf6 is a snapshot of a specific MF6 release —
  the generated classes are only valid for the DFNs they were built from. Right
  now that relationship is invisible: nothing in the installed package tells you
  which MF6 it was synced to, and nothing warns you if your binary is from a
  different release. You want to:

  1. Encode the contract — bake MF6_VERSION and DFN_SCHEMA_VERSION into a
  generated _contract.py so the package is self-describing.
  2. Check it at runtime — warn if an MF6 binary discovered on $PATH doesn't
  match.
  3. Make syncing a first-class UX — flopy4 mf6 sync [version] fetches DFNs,
  installs the binary, and regenerates the module in one command. Users never
  manually coordinate two separate tools again.

  This is a genuine improvement over flopy3: instead of undocumented version
  coupling requiring simultaneous releases, the version contract is explicit,
  checkable, and re-sync-able by the user on demand.

  ---
  Thorough Plan

  0. Prerequisites already in place

  - modflow_devtools.programs.install_program(program, version, bindir) — can
  install named MF6 binaries by version.
  - modflow_devtools.dfns.RemoteDfnRegistry(release_id=tag) — fetches and caches
  DFNs for a specific release.
  - modflow_devtools.dfn.fetch_dfns(owner, repo, ref, outdir) — already used by
  generate_classes.
  - modflow_devtools.dfns.CURRENT_SCHEMA_VERSION — "2.0.0.dev2" today.
  - generate_classes(ref=..., outdir=...) — the codegen entrypoint is already
  clean and callable from Python.

  1. Capture MF6 version during codegen

  generate_classes.py currently accepts ref (a git ref like "6.6.0" or
  "develop"). That ref is the MF6 version for tagged releases, but it's
  ambiguous for branches. The fix:

  - Add a mf6_version: str | None = None parameter to generate_classes(). When
  None, derive it from ref if ref looks like a semver tag (e.g. 6.6.0,
  6.7.0.dev0); otherwise leave it as None or the literal ref string. For the
  sync command (step 4), it will always be passed explicitly from the installed
  binary's reported version.
  - After codegen, write flopy4/mf6/_contract.py:

  # autogenerated file, do not modify
  MF6_VERSION = "6.7.0"
  DFN_SCHEMA_VERSION = "2.0.0.dev2"

  This is the one new file emitted by the pipeline. Its format is intentionally
  simple — just two string constants, no imports.

  2. Expose the contract in flopy4.mf6

  In flopy4/mf6/__init__.py:

  from flopy4.mf6._contract import DFN_SCHEMA_VERSION, MF6_VERSION

  Add both to __all__. A _contract.py should be committed to the repo for every
  release so an install from PyPI always has a known version. The initial
  committed file can use a sentinel like "unknown" if we're not ready to lock to
  a specific version yet, or we can gate on it with try/except ImportError.

  3. Runtime compatibility check

  New file flopy4/mf6/_compat.py (not autogenerated, lives alongside
  _contract.py):

  import shutil, subprocess, warnings, re
  from flopy4.mf6._contract import MF6_VERSION

  _VERSION_RE =
  re.compile(r"MODFLOW\s+6\s+version\s+([\d.]+(?:\.\w+)?(?:\+\w+)?)", re.I)

  def _query_mf6_version(exe: str) -> str | None:
      try:
          out = subprocess.check_output([exe, "-v"], text=True,
  stderr=subprocess.STDOUT)
          m = _VERSION_RE.search(out)
          return m.group(1) if m else None
      except Exception:
          return None

  def check_mf6_compatibility(exe: str | None = None) -> None:
      if exe is None:
          exe = shutil.which("mf6") or shutil.which("mf6.exe")
      if exe is None:
          return
      binary_version = _query_mf6_version(exe)
      if binary_version is None or binary_version == MF6_VERSION:
          return
      warnings.warn(
          f"flopy4.mf6 is synced to MF6 {MF6_VERSION} but the discovered "
          f"binary reports {binary_version}. Run `flopy4 mf6 sync` to re-sync.",
          UserWarning,
          stacklevel=2,
      )

  Call check_mf6_compatibility() at the bottom of flopy4/mf6/__init__.py — this
  runs once at import time. It's a no-op if no binary is on the path (the common
  CI/notebook case).

  Design choice to resolve: should a version mismatch be a UserWarning (soft,
  default) or RuntimeError (hard, opt-in via env var)? Probably start with
  UserWarning and add a FLOPY4_STRICT_MF6_VERSION=1 env var that promotes it to
  an error.

  Revised Plan: flopy4 mf6 sync

  Everything below reflects your clarifications.

  ---
  What the Dfns registry already gives us

  RemoteDfnRegistry caches raw .dfn files at registry.cache_path, and
  LocalDfnRegistry wraps a local directory. Both have a .spec property returning
  a Dfns object — but that's the new-API object (modflow_devtools.dfns.Dfns),
  whereas make.py currently uses the old-API Dfn/Dfn.load_all path (schema
  version 2.0.0.dev1). Bridging that gap is the upstream prerequisite.

  ---
  Prerequisite: upstream modflow_devtools PR

  Change DfnRegistry.spec from a property to a method with a schema_version 
  parameter.

  # modflow_devtools/dfns/registry.py
  class DfnRegistry(BaseModel):
      def spec(self, schema_version: str = CURRENT_SCHEMA_VERSION) -> Dfns:
          raise NotImplementedError

  class RemoteDfnRegistry(DfnRegistry):
      def spec(self, schema_version: str = CURRENT_SCHEMA_VERSION) -> Dfns:
          if not self.cache_path.exists() or not any(self.cache_path.iterdir()):
              self.sync()  # downloads v1 .dfn files to cache_path
          return Dfns.load(self.cache_path, schema_version=schema_version)

  class LocalDfnRegistry(DfnRegistry):
      def spec(self, schema_version: str = CURRENT_SCHEMA_VERSION) -> Dfns:
          return Dfns.load(self.path, schema_version=schema_version)

  Dfns.load() gains the schema_version parameter and dispatches to the
  appropriate to_v2_0_0_devN() migration function. The cache always holds
  original source files; the conversion is on-the-fly at load time. This is a
  clean separation: the registry owns fetch/cache, spec() owns schema migration.

  This PR is a prerequisite for everything downstream. It's narrow and shouldn't
  disturb existing callers since the current property becomes a zero-arg method
  call (breaking change, but this is a dev package under active development).

      Version is None for local DFNs (caller must query binary or leave as 
  'unknown').

      path = Path(release_id).expanduser()

⏺ These are good instincts. Let me think through the options clearly.

  The core tension: the version you want in _contract.py is "the MF6 version
  this module was synced to," but the DFN source doesn't reliably carry that
  information — floating tags need resolving, and local paths have nothing at
  all.

  Three candidate approaches:

  1. DFNs carry version metadata
  Ship a version.txt (or meta.toml) alongside DFN files — both in MF6
  distributions and in the registry cache. LocalDfnRegistry and
  RemoteDfnRegistry expose a version() method that reads it. This is the
  cleanest long-term solution: version travels with the DFNs, no out-of-band
  information needed. The problem is it requires MF6 to start including that
  file in distributions, which is another upstream change. For local paths from
  a dev checkout, version.txt already exists at the repo root — it's just not
  being bundled with the DFNs right now.

  2. Always get the version from the binary
  In the flopy4 mf6 sync flow, you install the binary first, then query it. The
  binary IS the authoritative source — it knows its own version including any
  +shortsha suffix. The DFN source is just a mechanism for getting the right
  DFNs; the version always comes from the binary. generate-mf6-classes (the
  lower-level dev tool) keeps --mf6-version as an explicit override.

  3. Registry resolves the tag
  registry.latest_tag() already exists and resolves @latest to a concrete tag.
  Use that as the version — it handles the floating tag case. Local paths still
  need the --mf6-version workaround, but that's a less common path.

  My opinion: option 2 is the most elegant for the sync command specifically,
  and option 1 is the right long-term answer for the lower-level tools. They're
  not mutually exclusive.

  The sync command's job is to align a binary and the module — so having it
  query the binary and use that version is semantically correct, not a
  workaround. The DFNs don't need to carry the version because sync is always
  binary-first.

  For generate-mf6-classes (used without a binary, e.g. in CI for class
  regeneration): use registry.latest_tag() to resolve the concrete tag for
  remote, and bundle a version.txt alongside the DFN files for local — that file
  could be populated from the MF6 repo's version.txt when get_dfns fetches
  them, or written explicitly by whoever populates the local DFN directory.

  Concretely: change flopy4 mf6 sync to always install the binary first, query
