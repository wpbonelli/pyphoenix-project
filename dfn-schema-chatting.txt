⏺ Big-picture assessment

  The overall direction — Pydantic, type-specific field subclasses, schema
  versioning — is sound. The three specific areas you flagged are worth
  scrutinizing before committing to an implementation strategy.

  ---
  1. Relation info: should it leave the component?

  The plan proposes moving parent/subcomponents from Dfn to
  DfnSpec.fixed_edges/free_edges. I'd push back on this.

  parent is intrinsic to a component: gwf-chd is always a GWF child. That's not
  context-dependent and not a spec-level concern — it belongs on Dfn. The
  subcomponents (what a component accepts as children, e.g. gwf-dis accepting
  utl-ncf) is similarly intrinsic to the accepting side. Moving this to DfnSpec
  makes individual Dfn objects less self-contained: you'd need the spec for
  context wherever you currently just inspect the component.

  The fixed_edges/free_edges split is genuinely useful as a conceptual
  distinction (fixed = child declares its parent; free = parent declares what it
   accepts), but the right representation is to encode both on the Dfn objects
  themselves — Dfn.parent for fixed, Dfn.accepts for free — and let DfnSpec
  derive any graph indices lazily from that. The current tree/to_tree() pattern
  is already doing essentially this.

  Recommendation: Keep relation info on Dfn. Rename subcomponents to accepts for
   clarity. The spec can build derived graph views; the component should be
  self-describing.

  ---
  2. Format layer: separate object vs. inference vs. co-location

  The plan's recommended Option 2 (a parallel FormatSpec alongside DfnSpec)
  solves the wrong problem. The principle "format and structure are separate"
  doesn't require separate objects — it requires clear labeling and selective 
  presence.

  Your intuition about inference is partly right: most block-level format
  behavior IS derivable from block name (griddata → READARRAY, options →
  keyword-value, period → depends on component). The block input style table in
  dfn_transforms.md confirms this for almost every case.

  The five field-level exceptions (layered, preserve_case, time_series,
  jagged_array, repeating) can't be fully inferred — but they're not all equal:
  - preserve_case is inferrable if you have a proper structural path type (which
   spec.py already distinguishes via path() vs field())
  - jagged_array is structural information about array shape (the row lengths
  are determined by another field); it arguably belongs in the structural type
  - time_series shapes how a field is parsed — but v2 already handles it
  structurally by retyping string+time_series → double; the annotation that
  remains is purely for the codec
  - layered and repeating are genuinely format-only

  Rather than a parallel object requiring two things to be threaded everywhere,
  co-locate format attributes as clearly-labeled optional members of the
  appropriate type-specific Pydantic subclasses: ArrayFieldV2.layered,
  ScalarFieldV2.time_series, etc. Consumers that don't care about format simply
  don't access those fields. You get the conceptual separation without the API
  overhead.

  Recommendation: No parallel FormatSpec. Keep format attributes on the relevant
   type-specific subclasses with clear naming, and derive block input style from
   block name at runtime. The "separation" is achieved by naming discipline and
  selective presence, not by physical separation into a second object.

  ---
  3. DFN-to-component mapping: 1-1 or not?

  This is the most foundational question. The WEL/WELG and RCH/RCHA pairs
  represent the same hydrological process with different input formats — the "G"
   variants exist purely to support array-format input. Under full
  format/structure separation, these should collapse to a single structural
  component with two format variants.

  But for v2, I'd argue against collapsing them, for two reasons:

  First, MF6 Fortran treats them as genuinely different readers — different
  FTYPE values, different Fortran modules. A v2 schema that merges them would
  create a mismatch between the schema and the thing it describes. The MF6
  tooling (which also consumes DFNs) would break.

  Second, the plan's stated goal is to formalize what exists before transforming
   it. Collapsing format variants is a design change to the MF6 input model, not
   a formalization of it. That's a separate (and bigger) decision.

  The right move for v2: keep 1-1 mapping, but make the relationship explicit
  via a variant_of: str | None attribute on Dfn. gwf-welg.variant_of = 
  "gwf-wel". This makes the conceptual structure visible in the schema without
  requiring surgery to the component model — and it positions a future v3 to
  unify them properly if MF6 itself ever does.

  Recommendation: Preserve 1-1 DFN-to-component mapping in v2. Add variant_of
  metadata to acknowledge the format-variant relationship. Reserve unification
  for a version where MF6 Fortran also unifies.

  ---
  Synthesis

  The plan's "separation of concerns" principle is right, but the implementation
   draws the boundaries in one place too many. The cleaner decomposition for v2
  is:

  - Structural schema (Pydantic type-specific field subclasses) — defines what a
   variable is, including format attributes co-located on the relevant
  subclasses
  - Component graph — expressed via parent/accepts on Dfn, derivable views on
  DfnSpec
  - Component identity — 1-1 with DFN files, format variants acknowledged via
  variant_of

  The parallel FormatSpec and the fixed_edges/free_edges split both add
  objects/concepts without a corresponding reduction in complexity elsewhere.
  The field subclass hierarchy and variant_of accomplish the same goals with
  less surface area.

  Does this alignment help clarify the path for Step 3?

⏺ Three good threads to pull on. Let me think through each carefully.

  ---
  preserve_case: always preserve?

  The reason case-folding exists in the first place is Fortran heritage. MF6's
  urword reader uppercases all tokens as it reads them — a convention carried
  from MODFLOW's history where keyword matching was case-insensitive by design.
  For MF6's own keyword comparison, casing doesn't matter; the Fortran code
  uppercases both the token and the expected keyword before comparing. So
  preserve_case was introduced specifically for the subset of string fields
  where the value must survive to the OS verbatim (file paths on Unix).

  Can we always preserve case? Yes, and I think we should. From the schema's
  perspective, if the Python codec simply never applies case-folding when
  writing, MF6's Fortran reader handles it fine — it does its own uppercasing
  for keyword matching and is indifferent to the case of incoming tokens for
  fields where case doesn't matter. There is no correctness issue. The only
  reason preserve_case exists as an explicit attribute is that urword doesn't
  naturally do this; it's a parser-side quirk, not a data model concern.

  Under "always preserve case", preserve_case disappears from the schema
  entirely. The path type still belongs in v2 — not to signal case behavior, but
   because a path is semantically distinct from an arbitrary string (it
  references a file, it resolves relative to a working directory, it may need
  validation). crs stays as string; the case issue for it evaporates.

  ---
  numeric_index: block repetition semantics

  I want to make sure I'm following your reasoning here, because numeric_index
  is considerably broader than the block_variable context. It appears on:
  - Block-variable fields (iper) — yes, these become block repetition keys in v2
  - Vertex/cell reference integers in packagedata (iv, iconn, ifno, etc.)
  - Connectivity arrays in DISU (ja — references to other cell numbers)
  - Cross-package feature references in advanced packages (LAK, SFR, MAW, UZF)

  If the argument for dispensing with it is "block keys have explicit index
  semantics from their structural role," that covers the iper-type cases
  cleanly. But for the broader set — ja, iv, and the dozens of in-record integer

  ---
  jagged_array: why is it needed?

  Let me reason through whether it's dispensable.

  The arrays annotated with jagged_array iac (all in DISU connectiondata) have
  shape (nja) — a flat 1D array of nja elements. Structurally, that's all the
  data model says: a flat array. The jagged structure (organized as n
  variable-length rows where row i has iac[i] elements) is only meaningful for
  the file reader, which must call READARRAY n times instead of once.

  So jagged_array is a pure codec concern — it controls how the flat (nja) array
   is read from the file. Structurally, the data is just array[nja]. That said,
  there are two principled ways to encode this without a separate annotation:

  Option A — richer shape grammar: Express the jagged structure in the shape
  itself, e.g. shape (nodes: iac) — "a ragged 2D array whose row i has iac[i]
  entries." This makes the jagged nature part of the structural description (the
   shape IS the data shape), and the codec reads from the shape grammar rather
  than a separate attribute. This is appealing because jaggedness IS a
  data-shape property, not just a reading hint.

  Option B — drop from schema, handle in codec: DISU is the only component with
  jagged arrays; the codec could have domain knowledge about this one case.
  Hacky, but the annotation only guards three DFN files.

  My instinct is Option A if we're willing to extend the shape grammar, which we
   probably should do anyway since the current shape strings are parsed
  informally. But the question stands: is jagged_array needed as a top-level
  field attribute at all, or is it really just a shape-grammar extension waiting
   to happen?

⏺ The Fortran source confirms what I suspected. Now I can answer all three

  ---
  jagged_array

  The Fortran IDM (InputParamDefinitionType) has no jagged_array field. Looking
  at gwf-disuidm.f90, ja is defined as plain INTEGER1D with shape NJA — the same
   as any other 1D integer array. The Fortran reader reads all nja values as a
  single contiguous free-format block; the per-node line organization in DISU
  input files is purely a user convention, not a structural reading mode.

  So jagged_array is completely invisible to the MF6 Fortran parser. It is
  exclusively a Python-side data presentation annotation: it tells flopy that
  the flat nja-element array logically organizes as nodes variable-length rows,
  one per node's connections, with row lengths given by iac. Whether flopy
  presents this as a flat array or a ragged list-of-lists is a UX question, not
  a structural schema question.

  It only appears on DISU because DISU is the only grid type with variable
  per-node connectivity. DIS and DISV have topologically regular grids; their
  connectivity is either implicit (DIS) or derived from geometry (DISV cell2d),
  not a separate jagged array.

  Conclusion: jagged_array should be dropped from the v2 structural schema. It
  is not a format annotation (the Fortran parser doesn't use it), not a
  structural annotation (the data is a flat 1D array), and is marginal even as a
   Python presentation hint — the relationship between ja and iac is already
  visible from the shapes (nja = sum(iac)), and any ragged presentation can be
  handled by the codec using that relationship without requiring a schema
  attribute.

  ---
  numeric_index

  Also absent from the Fortran IDM — iv in DISV vertices is just INTEGER with no
   index annotation. The 0/1 convention is domain knowledge in the Fortran code.
   numeric_index is purely a Python/flopy concern.

  And note: iper itself does not have numeric_index=true. The stress-period 0→1
  conversion in flopy is handled separately by the block repetition mechanism,
  not this attribute. So block repetition semantics cover the iper case, but
  numeric_index is a separate and broader set.

  The corpus breaks into four distinct categories:

  ┌─────────────┬───────────────────────┬───────────────────────────────────┐
  │  Category   │       Examples        │              Fields               │
  ├─────────────┼───────────────────────┼───────────────────────────────────┤
  │ List        │ ifno, lakeno, rno,    │ First column of                   │
  │ primary     │ mawno, uzfno, iv,     │ packagedata/vertices/cell2d — the │
  │ keys        │ icell2d               │  row identifier                   │
  ├─────────────┼───────────────────────┼───────────────────────────────────┤
  │ Foreign key │ lakeno/rno/ifno in    │ Integer referencing a primary key │
  │  references │ period blocks, iconn  │  in another list                  │
  │             │ in connectiondata     │                                   │
  ├─────────────┼───────────────────────┼───────────────────────────────────┤
  │ Topology    │ ja, icvert            │ Integers referencing cell/vertex  │
  │ references  │                       │ numbers by position               │
  ├─────────────┼───────────────────────┼───────────────────────────────────┤
  │ Mixed       │                       │ String field that accepts either  │
  │ string/int  │ utl-obs id, id2       │ a cell name OR a 1-based cell     │
  │             │                       │ number                            │
  └─────────────┴───────────────────────┴───────────────────────────────────┘

  The first three categories share a common structure: an integer whose value is
   a 1-based index into some named collection (a feature list, a vertex list, a
  grid node list). These are all effectively foreign keys or primary keys. If
  the v2 schema models list primary keys explicitly — e.g., a ListFieldV2 knows
  which of its record columns is the key — then categories 1 and 2 both fall out
   of the structural role without any explicit annotation. Category 3 is similar
   if grid nodes are treated as an implicit indexed collection.

  The fourth category (utl-obs id/id2) is genuinely hybrid: the field is
  declared string because it accepts either a cell name OR a 1-based integer
  string. This can't be resolved by key-column modeling alone; it requires
  either a union type or a retained annotation.

  Bottom line: numeric_index can largely be eliminated if v2 introduces explicit
   key-column semantics on ListFieldV2. The 0/1 conversion becomes a consequence
   of a field's structural role (is it a key column of a list, or a reference to
   one?) rather than an explicit annotation. The utl-obs edge case needs
  separate treatment — possibly as a cellid_or_name type or a retained
  annotation on that specific field.

⏺ Pydantic pattern for PK/FK semantics

  Pydantic has no built-in PK/FK concept (it's not an ORM). The closest thing in
   the ecosystem is SQLModel's Field(primary_key=True), which is just metadata
  carried on an Annotated type. We should design what we actually need rather
  than stretching an existing pattern.

  The structure here is:

  - Every list field has at most one primary key column — the integer that
  identifies each row (feature number, vertex number, etc.). Always equal to the
   1-based row index.
  - integer fields elsewhere that reference one of those keys are foreign keys —
   same 0/1 conversion, different structural role.
  - Not all integers are indices — nlay, maxbound, nper, etc. are counts, not
  references.

  The cleanest Pydantic encoding:

  class ScalarFieldV2(BaseModel):
      type: Literal["keyword", "integer", "double", "string", "path"]
      name: str
      index: bool = False   # 1-based in file; 0-based in Python
      # ... time_series, valid, optional, etc.

  class ListFieldV2(BaseModel):
      type: Literal["list"]
      name: str
      item: RecordFieldV2 | UnionFieldV2
      key: str | None = None   # names the primary-key column in item

      @model_validator(mode="after")
      def _key_exists_and_is_index(self):
          if self.key is not None and isinstance(self.item, RecordFieldV2):
              field = self.item.fields.get(self.key)
              if field is None or not getattr(field, "index", False):
                  raise ValueError(f"key {self.key!r} must name an index=True
  field")
          return self

  index replaces numeric_index — same semantics, cleaner name. It marks:
  - the primary key column of a list (always has index=True, named by
  ListFieldV2.key)
  - any integer foreign key that references such a column elsewhere (period
  block feature references, connectiondata, vertices references in cell2d, etc.)

  The model_validator on ListFieldV2 enforces internal consistency — the
  declared key must be an index field. Cross-list FK consistency (e.g. verifying
   that lakeno in a period block references the lakeno primary key in
  packagedata) requires a component-level or spec-level validator, since you
  need both the period block and the packagedata block in scope at once. That's
  worth having but doesn't need to be in the field model.

  The one wrinkle: topology/connectivity references (ja, icvert, etc.) reference
   grid node or vertex numbers, not a list primary key in the same component.
  They still get index=True; the target collection is implicitly the grid node
  set. You could add an optional target: str | None = None to ScalarFieldV2 to
  make that explicit, but I'd leave it unset for now — the codec already knows
  grid node references from context, and adding it opens the question of how to
  name cross-component collections cleanly.

  ---
  utl-obs id/id2 as union

  Yes, straightforwardly. The field accepts either a boundary name (string) or a
   cell ID (1–3 integers depending on grid type). In v2:

  UnionFieldV2(
      name="id",
      arms={
          "name": ScalarFieldV2(type="string"),
          "cellid": ScalarFieldV2(type="integer", index=True),   # DISU: single
  node
          # or RecordFieldV2 for DIS/DISV multi-integer cellids
      }
  )

  The cellid form is already modeled elsewhere as a RecordFieldV2 (DIS:
  layer/row/col; DISV: layer/cell). You'd reference the same shared type. The
  index=True on the integer arm handles the 0/1 conversion for the numeric case.
   The string arm gets no conversion. The union discriminates at parse time by
  whether the value is numeric or not, which is exactly what MF6 already does.
