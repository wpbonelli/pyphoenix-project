⏺ The overall vision is still consistent. The five-type discriminated union,
  block-type inference from structural composition, attribute lifecycle
  decisions, and component relationship model are all coherent and
  self-consistent. The WPB notes fall into three categories: requests for
  clarification, questions about whether an attribute is actually necessary, and
   a gap where design specifics are missing.

  Here's my read on each:

  ---
  time_series — "bypass numeric validation" / why on scalars?

  "Bypass numeric validation" means: if a field is declared double precision in
  v1, the parser validates the token is actually numeric and rejects a TS name
  string. By declaring it string, v1 authors worked around this. The structural
  type is double; that's why v2 retypes them. As for scalars vs. arrays — period
   block columns like recharge or head are scalar columns in records (one value
  per cell per row), not arrays, and those are precisely where time_series=True
  is most common. The array form (READARRAY double with time_series) means the
  whole array can be replaced by a TS reference. Both are valid uses.

  layered — "isn't this an MF6 parser concern?"

  Partly yes. It controls whether the codec emits one READARRAY invocation or N.
   But it can't be dropped because nlay in shape is necessary but not sufficient
   — some nlay-shaped arrays are NOT layered (there are counter-examples in the
  corpus). Unless we make it derivable by some other means, it has to be
  explicit. Worth checking whether we can find a clean rule that makes it
  derivable; if so, drop it.

  repeating — "I'd like to drop this if possible"

  I'd lean toward dropping it too. The one active use (utl-tas tas_array) could
  be modeled as a ListFieldV2 with an array item type rather than a scalar field
   with repeating=True. That's more principled and uses existing machinery.
  Worth verifying utl-tas's actual structure before committing.

  just_data — "how exactly does utl-tas look?"

  A begin timeseries NAME block whose body is just raw READARRAY data with no
  keyword prefix — the block header IS the label. The just_data flag told the v1
   parser to skip looking for a field keyword and read the body directly. In v2,
   if the block has a label field (the TAS name on the begin line) and contains
  a single unlabeled READARRAY field, that's inferrable from structure — no
  attribute needed. This reinforces dropping just_data.

  netcdf — keep for now

  Agreed, consistent with the current plan. The table cell already says "keep
  for now?" — just change the question mark to a definitive "keep until MF6 IDM
  fully supports netcdf, then drop."

  READARRAY vs. keyword-value — "isn't READARRAY a special case?"

  Superficially similar (keyword precedes value), but the reader is entirely
  different: READARRAY consumes multiple lines, supports
  constants/binary/layered invocations, and has its own token grammar. urword
  reads a single token on the same line. Keeping them as distinct block types is
   correct — the distinction is meaningful for the codec.

  Repeating blocks — "what's the specific mechanism?"

  This is the genuine gap — the document says "first-class block repetition"
  without specifying it. The design needs a concrete Block attribute, something
  like Block.label_field: str | None, naming the field that appears on the
  begin/end line (not in the body). When set, the block can repeat with
  different labels. The iper period-block field becomes a
  ScalarFieldV2(type="integer") referenced by Block.label_field="iper", removed
  from the block body's field list. Similarly for utl-ts timeseries/utl-obs
  continuous blocks. This needs to be written into the doc.

  Cross-component FKs — "only grid node indices?"

  Mostly, yes. True cross-component integer FKs (integer in component A →
  specific row in a DFN-defined list in component B) are rare. Most
  cross-component references are string-based (package names, observation
  names). Grid node/cell references aren't DFN-defined lists. Worth auditing the
   corpus to confirm, but the existing index=True approach likely handles all
  real cases.

  ---
  The two things that need concrete resolution before implementation: (1) the
  Block.label_field mechanism for repeating blocks, and (2) whether repeating
  can be dropped in favor of modeling utl-tas as a list. Want to work through
  those first?

⏺ Here's what the corpus data tells us, question by question:

  ---
  time_series — fuller explanation

  The MF6 Fortran parser works like this: urword always reads a raw string
  token. For a field typed double precision, the parser immediately calls a
  numeric-conversion routine on that token — if it fails (because the token is
  "HEAD_TS" instead of "1.0"), it's a fatal error. By declaring the field
  string, v1 authors bypass that immediate conversion: the raw string is stored
  as-is, and higher-level code (flopy, etc.) decides whether it's a TS name or a
   number.

  So "bypass numeric validation" means: avoid the Fortran parser crashing when
  it encounters a non-numeric string in what is semantically a numeric field.

  On arrays: the six readarray fields with time_series=true are
  gwf-rcha.recharge, gwf-rcha.aux, gwf-evta.rate, gwf-evta.aux,
  utl-spca.concentration, utl-spca.temperature. For these, rather than providing
   inline READARRAY data, you can reference a TAS object — the READARRAY routine
   checks whether the token is a TAS reference and, if so, fetches the array
  from the TAS. Semantically analogous to the scalar case (temporal sourcing),
  but the mechanism is READARRAY-level, not urword-level. Both are real uses.

  ---
  layered — drop it, fully derivable

  The corpus search is definitive: every readarray field with nlay in its shape 
  has layered=true. Zero exceptions. The rule is perfect:

  ▎ ArrayFieldV2 is layered iff nlay appears in its shape expression.

  This isn't a coincidence — it's logically necessary. The MF6 READARRAY routine
   reads a layered array by making one READARRAY call per layer (using the
  LAYERED keyword). Any array with nlay in its shape must be read this way;
  there's no alternative reading path. So layered is entirely derivable. Drop
  it.

  ---
  repeating — what utl-tas actually does

  From utl-tas.dfn, the structure is:

  # attributes block — defines N named time-array series
  begin attributes
    name TAS1 TAS2 ...   # time_series_name has shape (any1d) — N names
    method LINEAR
  end attributes

  # time block — repeats once per time point (labeled by time_from_model_start)
  begin time 0.0
    [READARRAY data for TAS1]   # tas_array occurrence 1
    [READARRAY data for TAS2]   # tas_array occurrence 2
    ...                          # one per named TAS
  end time 0.0

  begin time 1.0
    [READARRAY data for TAS1]
    [READARRAY data for TAS2]
  end time 1.0

  So repeating=true on tas_array means: within a single block occurrence, this
  field appears N times — once per named TAS in the attributes block. N is
  determined by the count of names in time_series_name.

  Your "2D collection" framing is apt: it's N independent READARRAY calls, one
  per TAS name. The count isn't fixed in the schema; it's determined at runtime
  by the attributes block content. That makes it awkward to represent as a plain
   ListFieldV2 (lists have a uniform row type, not a variable count of
  full-array items).

  Given it's the only active case and the count is dynamically bound, the
  pragmatic call is: keep repeating: bool as a schema marker, handle the
  TAS-specific semantics in the codec. The block-class label mechanism handles
  the "repeating block" part; repeating on the field handles the "field repeats
  N times within a block occurrence" part. These are distinct.

  ---
  Block class and labeled blocks — yes, combine them

  Your instinct is right. We need a Block schema class. The just_data case and
  the labeled/repeating block case are part of the same design:

  class Block(BaseModel):
      name: str
      fields: dict[str, FieldV2]
      label_field: str | None = None   # field appearing on begin/end line, not 
  in body
      optional: bool = False

  When label_field is set, the block is "labeled" — it can repeat with different
   label values (e.g., begin period 3, begin time 0.5). The label field is
  excluded from the block body's field list. With this, block_variable=true in
  v1 maps cleanly to: the field named by Block.label_field, removed from
  Block.fields.

  The just_data case falls out naturally too: a block whose only body field has
  no keyword prefix (derivable from field structure — it's an unlabeled
  readarray field with tagged=false). No explicit attribute needed.

  ---
  Cross-component FKs — concrete cases

  Three distinct patterns in the corpus:

  1. Grid topology integers (gwf-disu.connectiondata.ja, iac): cell numbers in
  the unstructured grid. These reference grid nodes, not a DFN-defined list with
   a declared PK. index=True for 0-based conversion is sufficient; no FK
  declaration.
  2. Within-component cross-block FKs (gwf-sfr.connectiondata.ic): references
  SFR's own reach numbers. Shape is even (ncon(ifno)) — per-row variable length.
   Within-component; index=True handles codec conversion.
  3. gwf-mvr.period.id1: genuinely cross-component. References a row in another 
  package's packagedata list — the package is identified at runtime by
  pname1/mname1 string. The FK is untyped: id1 can be a well number (MAW), reach
   number (SFR), UZF cell, or lake outlet depending on what pname1 resolves to.
  This is not a statically typed FK; the codec resolves it against the named
  package at runtime. index=True for 0-based conversion is again sufficient — we
   don't need a formal FK declaration because the target is dynamic.

  Summary: There are no cross-component FKs that require a formal FK declaration
   in the schema. index=True on the FK column plus the existing PK/key design is
   sufficient in all cases.
