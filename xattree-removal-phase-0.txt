⏺ I've completed the audit (Task #1). Two findings worth flagging before I start
  changing code — one is a plan-scope correction, the other is a technical
  landmine that changes how I'll implement step 3.

  1. Scope correction: The plan assumed dis/disv/tdis/ncf (hand-written,
  skip-listed in dfn2py.py) still use the old block= convention. They don't — I
  checked, and they already carry dfn_block/dfn_type metadata (written in the
  codegen-v2 style, presumably copy-pasted from generator output during PR
  #327's "update model dis/disv"). So the real fix touches 79 files, ~796 
  occurrences of dfn_block: 71 auto-regenerated (fixed for free by step 6) + 8 
  hand-written files that dfn2py.py skips and won't regenerate (gwf/dis.py,
  gwf/disv.py, gwf/disbase.py, gwt/dis.py, gwe/dis.py, prt/dis.py, tdis.py,
  utl/ncf.py) that I'll need to fix by hand/script. Mechanical, just bigger than
  the plan's "76" estimate.

  2. Technical landmine in step 3's literal wording. The plan says emit fields
  via flopy4.mf6.spec.field(block=...) instead of raw
  attrs.field(metadata={"dfn_block":...}). I traced spec.field() →
  flopy4.spec.field() → the real xattree.field(), and confirmed:
  xattree.field(converter=...) doesn't hand the converter to attrs directly — it
  stashes it in metadata["xattree"]["converter"], and that only gets applied by
  a field_transformer that runs inside the @xattree class decorator. Codegen-v2
  Package subclasses are deliberately plain @attrs.define (not
  @xattree-decorated — that's the whole point of PR #336's "decouple xattree
  from codegen"). So if I literally switch generated Path-record fields
  (budget_file, ts6_filename, etc., which currently use raw
  attrs.field(converter=_optional_path, metadata={...})) to call
  spec.field(converter=_optional_path, ...), the converter would silently stop
  running — string paths would no longer coerce to Path objects. Currently they
  work because they call raw attrs.field() directly.

  My resolution: keep codegen-v2 fields on raw attrs.field(default=..., 
  converter=..., metadata={...}) (unchanged mechanism, so converters stay
  real/active), but fix the actual root cause the plan cares about — rename the
  metadata key dfn_block → block everywhere (confirmed correct independently:
  netcdf.py:112 already does "block": f.metadata.get("dfn_block", "") as a
  workaround shim, i.e. the rest of the codebase already expects the key to be
  called block). Hand-written xattree classes (Gwf, Simulation, etc.) keep using
  the real spec.field()/array()/dim() as today — unchanged. This achieves the
  plan's actual goal (one metadata key, one fields_dict()/blocks_dict() that
  sees every field, one structuring/unstructuring path) without the regression.

  I'll proceed on this basis unless you want it done differently.

⏺ Confirmed — and it's actually necessary, not just cleaner. I found that
  hand-written @xattree classes already do field(converter=convert_grid, ...)
  and path(converter=to_path, ...) (e.g. simulation.py:26,
  gwf/__init__.py:154,163). Tracing xattree.field()'s source: it never forwards
  converter/validator to the underlying attrs.field() call — it stashes them in
  metadata["xattree"], and they only get reattached as real attrs converters by
  a field_transformer that runs inside @xattree-decorated classes. So those
  existing call sites only work because their enclosing classes (Simulation,
  Gwf, etc.) are @xattree-decorated. Codegen-v2 classes aren't, so the same call
  would silently drop the converter — exactly the landmine, just already latent
  in the existing API, not something switching codegen-v2 over would newly
  introduce.

  Fix: change flopy4/spec.py's field() (the single base function both
  flopy4/mf6/spec.py's field() and path() delegate to) to build the
  attrs.field() call directly — passing converter/validator for real — while
  still stamping the same metadata["xattree"] = {"kind": "attr", "converter": 
  ..., "validator": ...} shape xattree.field() produces, so @xattree classes'
  field_transformer/get_xatspec() keep working unchanged (the reattachment
  becomes redundant but harmless there). This fixes the landmine for codegen-v2
  and makes the existing hand-written converter usages correct by construction
  rather than by accident.
