  Poster recommendations for flopy4 / pyphoenix

  A few questions first

  Before the sketches — a few things would sharpen the design:

  1. Conference and audience — is this AGU, the MODFLOW Users Group Meeting, or
  something else? MUG attendees are almost all active flopy users; AGU is
  broader.
  2. Status of the project — is flopy4 available as a pip-installable
  alpha/beta, or still pre-release? That changes how you frame the call to
  action.
  3. Specific design decisions you're most uncertain about — from the code I can
  see several candidates (the parent= vs dict-assembly construction styles, the
  {kper: {cell_id: value}} dict syntax, FILL_DNODATA sentinel vs masked arrays,
  etc.). Which ones genuinely need community input?
  4. Poster dimensions and tool — A0 portrait? PowerPoint, Inkscape,
  LaTeX/beamer?

  ---
  Key design differences I found

  These are the poster-worthy contrasts:

  Area: Output data
  flopy3: HeadFile.get_alldata() → raw numpy array
  flopy4: open_hds() → labeled xr.DataArray with named dims (layer, row, col,
    time); .sel(layer=0) works
  ────────────────────────────────────────
  Area: Package construction
  flopy3: MFSimulation → MFModel → package constructors return packages
  flopy4: parent= registers at construction, or dict-assembly at model level
  ────────────────────────────────────────
  Area: Stress period data
  flopy3: MFTransientList / stress_period_data={...} flopy-specific dict types
  flopy4: {kper: {(l,r,c): val}} plain Python; "*" wildcard; or full numpy array

    with FILL_DNODATA
  ────────────────────────────────────────
  Area: Vertex/unstructured grids
  flopy3: Limited; separate code paths
  flopy4: First-class via xugrid; open_hds() returns xu.UgridDataArray for DISV
  ────────────────────────────────────────
  Area: NetCDF I/O
  flopy3: External; manual
  flopy4: Built-in CF-compliant + UGRID-mesh write; NetCDFModel.from_model(gwf)
  ────────────────────────────────────────
  Area: Sync with MF6 releases
  flopy3: Manual regeneration
  flopy4: flopy4 mf6 sync CLI; classes auto-generated from upstream DFNs
  ────────────────────────────────────────
  Area: Inspection
  flopy3: .get_data() / custom repr
  flopy4: .data → xr.Dataset; .stress_period_data → pd.DataFrame

  ---
  Framing advice

  The core awkwardness with a "new version" poster: nobody wants to hear "we
  rewrote everything" when they have 10,000 lines of working flopy3 code.
  Reframe around what users gain, not what changed architecturally.

  The audience has just taken a short course, so don't use poster space to
  explain basics. Use it for:

  1. Side-by-side code comparisons — the API is the product for this community.
  A well-chosen before/after is worth 500 words of prose.
  2. Specific feedback prompts — not generic "what do you think?" but concrete
  choices: "Which construction style do you prefer for building a simulation?"
  with both patterns shown.
  3. A QR code to something actionable — GitHub Discussions, a short Google
  Form, or a pre-opened issue. Poster QR codes get scanned in the first 30
  seconds; make the landing page count.

  The right tone: "We made hard choices — help us know if we got them right."
  That's honest, engages experts, and gives you genuinely useful signal.

  ---
  My concrete recommendations

  Go with Layout C (or a refinement of it). Reasons:
  - The before/after code comparison is the strongest asset you have — it's
  concrete, immediately legible to your audience, and doesn't require
  explanation
  - Three focused feedback questions are better than a general "tell us what you
  think" — you'll get higher response rate and more useful signal
  - The QR code goes to something synchronous (a form, not just a repo link) so
  people who scan it while standing there will actually complete it
  - Keep prose to an absolute minimum; this audience reads code faster than
  sentences

  Specific code to feature in the comparison:

  flopy3 side — the standard quickstart: MFSimulation, ModflowGwf,
  ModflowGwfdis, ModflowGwfchd, then HeadFile(...).get_alldata() returning a
  numpy array.

  flopy4 side — same model, showing: parent= construction,
  chd.data.head.sel(kper=0), gwf.output.head.squeeze(), and
  head.plot.imshow(ax=ax) with the xarray plot integration. Then one extra cell:
  a DISV model result as xu.UgridDataArray — something that's genuinely new.

  For feedback questions, the three I'd prioritize based on the design decisions
  I see in the code:
  1. parent= vs explicit dict-assembly construction — both patterns exist, which
  do users find more natural?
  2. {kper: {(l,r,c): val}} dict syntax vs full numpy arrays with FILL_DNODATA —
  which do users reach for first?
  3. Named-dimension xarray output — does this actually change how you'd
  interact with model results, or is it noise?
