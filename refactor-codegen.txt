⏺ Now I have a clear picture. Here's my analysis:

  ---
  _get_block() and _set_block() are not duplicating the converter layer's 
  purpose, but they do introduce a subtle redundancy worth raising.

  What each layer actually does

  Converter ingress (structure_component): Parses raw MF6 file token rows into a
   {col_name: np.array} dict, handling 1-based→0-based index conversion, cellid
  tuple packing, optional column detection, etc. Passes the result as a
  constructor kwarg (e.g., Lak(packagedata=the_dict, ...)).

  _set_block(): Receives that dict (or a user-supplied DataFrame/Dataset) in
  __attrs_post_init__ and scatters it into individual xattree-tracked attrs
  (packagedata_ifno, strt, nlakeconn, …), including dimension validation and
  xattree tree re-dimensioning. It also serves as the property setter for
  user-facing assignment (lak.packagedata = df).

  _get_block(): Reassembles those individual attrs back into an xr.Dataset —
  user-facing only.

  Converter egress (_unstructure_component): Has new _LIST_BLOCK_NAMES logic
  that similarly re-assembles individual xattree DataArrays into a Dataset — but
   for the writer, not the user.

  So these are genuinely distinct responsibilities: parse → scatter → user-view 
  → serialize. No layer is fully replacing another.

  The real concern: col_map is repeated 3× per block in generated files

  In lak.py (and any similar generated package), the same column mapping appears
   in:
  1. __block_col_maps__ (ClassVar) — used by structure_component
  2. __attrs_post_init__ — passed inline to _set_block
  3. Property getters/setters — passed inline again to _get_block/_set_block

  __block_col_maps__ is already the single source of truth for the converter.
  _set_block/_get_block could simply look up
  type(self).__block_col_maps__[block_name] instead of taking col_map as a
  parameter, removing the redundancy from the generated code. That would also
  make _set_block's signature shorter and the generated __attrs_post_init__ and
  properties much less verbose.

  The minor logic duplication

  The 2D-int-array → object-array-of-tuples cellid packing appears in both
  _set_block (package.py) and structure_array (structure.py). These handle
  different pathways (user-supplied arrays vs. ingress converter output), but
  the logic is the same and could be extracted to a shared helper if desired.

  Bottom line

  The methods are warranted — they fill a real gap (user-facing block API +
  __attrs_post_init__ bridge). But it's worth suggesting that
  _set_block/_get_block should consume __block_col_maps__ by block name rather
  than accepting a repeated inline col_map, which would eliminate the 3×
  repetition in every generated package file that has list blocks.

  ---
  Yes — I think the approach in this PR is building a significant amount of
  machinery to solve a problem that largely dissolves if you change the
  representation.

  Here's the core issue. A static list block like packagedata in LAK is a table
  — a well-defined set of rows with a fixed schema. The PR maps it to N separate
   xattree-tracked NDArray attrs (one per column), then uses __block_col_maps__,
   _set_block, _get_block, a _packagedata buffer, and __attrs_post_init__ to
  reassemble them into a Dataset for the user. That's: table → fan out into N 
  columns → reassemble back into table. The round-trip is the complexity.

  The v2 DFN schema makes this concrete: List.item: Record | Union is a single
  typed field, and the impl plan says "a List field maps to a typed list
  attribute." The schema already knows nlakes derives from len(packagedata) —
  that's derived_dims: sum(packagedata.nlakeconn). Storing nlakes as a separate
  xattree dim attr is redundant with the list itself.

  What the simpler version looks like

  For static tabular list blocks (uniform record item type — packagedata,
  connectiondata, outlets):

  # PR: ~80 lines per block
  nlakes: Optional[int] = dim(block="dimensions", ...)
  packagedata_ifno: Optional[NDArray[np.int64]] = array(block="packagedata",
  dims=("nlakes",), ...)
  strt: Optional[NDArray[np.float64]] = array(block="packagedata",
  dims=("nlakes",), ...)
  # ... 3 more columns
  __block_col_maps__: ClassVar[dict] = {"packagedata": {...}}
  _packagedata: Optional[dict] = attrs.field(alias="packagedata", ...)
  def __attrs_post_init__(self): ...
  @property def packagedata(self): ...
  @packagedata.setter def packagedata(self, v): ...

  # Simpler: 1 line per block
  packagedata: Optional[pd.DataFrame] = field(block="packagedata", default=None)
  connectiondata: Optional[pd.DataFrame] = field(block="connectiondata",
  default=None)
  outlets: Optional[pd.DataFrame] = field(block="outlets", default=None)

  nlakes becomes a property deriving from len(packagedata), not a stored dim.
  _set_block, _get_block, __block_col_maps__, and _packagedata all disappear.
  The converter's _parse_list_block_rows already produces {col: array} — one
  pd.DataFrame(...) call converts it. On egress, you iterate rows.

  The three block types are different

  It's worth distinguishing them clearly, because they don't all simplify the
  same way:

  1. Static tabular list blocks (packagedata, connectiondata, outlets) — uniform
   record item type, no period dimension. DataFrame is the natural Python
  representation. This is where the PR's fan-out is most unnecessary.
  2. Stress period data (CHD, WEL, DRN) — sparse, keyed by cellid, varies per
  period. The current xarray sparse approach makes sense here because you do
  want the (nper, nodes) dimensional structure for operations. This is the
  hardest to simplify and probably the right place to keep xattree involved.
  3. Keystring period blocks (OC save_head, STO steady_state) — the PR already
  simplifies these relative to the old PrintSaveSetting nested class, replacing
  them with NDArray[np.str_] keystring fields. That direction looks right.

  What changes in the converter

  The ingress structure_component already does the hard work:
  _parse_list_block_rows produces {col_name: np.array}. If the target field is a
   pd.DataFrame, it's pd.DataFrame(_parse_list_block_rows(...)) — one line. The
  egress is also straightforward: iterate df.itertuples(), write tokens.

  The _LIST_BLOCK_NAMES set in egress and the Dataset-reassembly logic also goes
   away — the writer just knows "if it's a DataFrame, write it row-by-row."

  The xattree question

  xattree won't track a pd.DataFrame field as a DataArray, but that's fine —
  static list blocks aren't gridded data and don't need dimensional xarray
  semantics. The tension here is that xattree was chosen as the universal model
  for all package fields. If list blocks opt out of that, you need to decide
  whether that's acceptable. Given that you're already reconsidering the
  fan-out, it seems like the answer is yes — xattree's role is probably most
  appropriate for gridded/dimensional arrays, not tabular lists.

  Bottom line

  The fan-out pattern in this PR was motivated by "try to conform to the xarray
  data model," and the PR's own _get_block immediately reconstructs a Dataset
  from those fanned-out columns. That tells you the fan-out isn't buying
  anything — it's just an internal representation choice that adds machinery.
  Given the v2 DFN schema's explicit List type and the impl plan's direction, a
  DataFrame (or list of records for union item types) per list block is the
  right representation, and it eliminates _set_block, _get_block,
  __block_col_maps__, the per-column attrs, and the _packagedata buffer
  entirely.

  The right time to surface this is before the code generator encodes the
  fan-out pattern across all packages. The generated output for a package like
  LAK would go from ~250 lines to ~30.
