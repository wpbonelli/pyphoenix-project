❯ Consider the design of the object model in this project, in particular for    
  fields that are recarrays in the v1 DFNs: packagedata, period blocks, etc.    
  Note how we have decided to "fan out" these fields into distinct arrays to    
  fit the xarray data model so far, in some cases departing from the field      
  structure as defined in the v1 DFNs. The OC package is an example of this. We 
   are reconsidering this design decision. It introduces complexity in          
  initialization/modification, as well as for code generation and in the codec  
  and the converter layer (structuring/unstructuring), besides the conceptual   
  complexity of the Python class definitions looking unlike what one might      
  expect after reading the DFN. Instead of this fan-out and recombination       
  approach, I'm thinking we could just make list fields `list[ItemType]` in the 
   class definitions, where `ItemType` is some record classa, or a union of     
  record classes (called "keystring" in the v1 DFNs), as per the pattern we     
  have tried where we have a class for each record type. We could have          
  pd.DataFrame and xr.Dataset views of this, then, maybe? The latter of which   
  could fan-out columns, perhaps optionally. But the basic idea being to keep   
  lists as lists and map that into other views when needed. This seems like it  
  would simplify things and let us remove a lot of custom code. Probably also   
  make for faster IO due to less transformation necessary? Read the developer

⏺ I now have a thorough picture of the design, the issues, the in-flight codegen
   PR, and the prior analysis in refactor-codegen.txt. Here's my recommendation.

  ---
  Recommendation: Adopt list[ItemType] as primary representation for all list 
  fields

  TL;DR

  The fan-out is the wrong invariant to maintain. The list[ItemType] design
  you're considering is strictly better. The core principle: the Python
  representation should match the DFN structure; xarray views are derived on
  demand, not the ground truth.

  ---
  The problem with the current fan-out

  The current design takes a DFN list field — which is structurally a sequence
  of (col1, col2, ...) rows — and explodes it into N separate NDArray attrs, one
   per column, all sharing the same dimension. This creates a round-trip that's
  purely internal: rows → scatter into columns → reassemble into rows.
  Everything between scatter and reassemble is accidental complexity:

  - __block_col_maps__, _packagedata buffer, _set_block, _get_block,
  __attrs_post_init__: all exist to service the round-trip
  - structure_array is 700+ lines handling a dozen cases for what is ultimately:
   "parse some rows"
  - _hack_period_non_numeric in the egress is a pile of special cases for OC
  that wouldn't exist if OC's period data were a list of records
  - The egress _LIST_BLOCK_NAMES set and Dataset-reassembly logic exist purely
  because the egress needs to undo the scatter before writing rows
  - LAK in PR #310 is 561 lines, the majority being column attrs; it should be
  ~80

  The v2 DFN schema says List.item: Record | Union. That maps cleanly to
  list[ItemType] in Python. The schema is right.

  ---
  Proposed design by field category

  1. Static list blocks (packagedata, connectiondata, outlets, tables, etc.)

  These are tables with a fixed schema, no time dimension. Use
  Optional[list[ItemType]] where ItemType is a generated dataclass or attrs
  class corresponding to the DFN record definition:

  @dataclasses.dataclass
  class LakPackagedataItem:
      ifno: int
      strt: float
      nlakeconn: int
      aux: list[float] | None = None
      boundname: str | None = None

  @xattree
  class Lak(Package):
      packagedata: Optional[list[LakPackagedataItem]] =
  field(block="packagedata", default=None)
      connectiondata: Optional[list[LakConnectiondataItem]] =
  field(block="connectiondata", default=None)

      @property
      def nlakes(self) -> int | None:
          return len(self.packagedata) if self.packagedata else None

  nlakes and similar derived dimensions become computed properties — they're
  len(list_field), not stored attrs. The entire __block_col_maps__, _set_block,
  _get_block, dim buffer, and __attrs_post_init__ machinery disappears.

  2. Repeating period blocks with sparse spatial structure (CHD, WEL, DRN, RCH, 
  etc.)

  These are blocks that repeat per stress period, where each block is a sparse
  list of active cells. The natural representation is dict[int, list[ItemType]]
  — a fill-forward sparse map from period index to list of records:

  @dataclasses.dataclass
  class ChdPeriodItem:
      cellid: tuple[int, ...]
      head: float
      aux: list[float] | None = None
      boundname: str | None = None

  @xattree
  class Chd(Package):
      period: Optional[dict[int, list[ChdPeriodItem]]] = field(block="period",
  default=None)

  This is semantically equivalent to flopy3's stress_period_data, which is
  already what users understand. The fill-forward logic lives in the converter
  (or the dict[int, ...] API itself), not scattered through structure_array.

  3. Repeating period blocks with non-spatial content (OC, STO)

  OC period blocks are lists of keystring records. STO period blocks are just a
  flag. These are cleaner as records too:

  # OC
  @dataclasses.dataclass
  class OcPeriodItem:
      action: Literal["SAVE", "PRINT"]
      rtype: str  # HEAD, BUDGET
      setting: str  # ALL, FIRST, LAST, STEPS n1 n2...

  @xattree
  class Oc(Package):
      period: Optional[dict[int, list[OcPeriodItem]]] = field(block="period",
  default=None)

  For STO, period: Optional[dict[int, Literal["STEADY-STATE", "TRANSIENT"]]] or
  similar — one entry per period, no list needed.

  ---
  Views: DataFrame and xr.Dataset on demand

  For tabular list blocks (static, uniform Record item type), a to_dataframe()
  method:

  def packagedata_as_df(self) -> pd.DataFrame | None:
      if self.packagedata is None: return None
      return pd.DataFrame([dataclasses.asdict(r) for r in self.packagedata])

  For spatial period data, an xr.Dataset view that fans out columns and
  materializes the full-grid representation:

  def period_as_dataset(self) -> xr.Dataset | None:
      # materialized from the list, not stored
      ...

  This is the key reversal: the fan-out becomes a view, not the primary storage.
   The view is computed on demand and doesn't need to be kept in sync.

  ---
  Impact on the converter

  structure_array largely disappears. The ingress for a list block is:

  rows = parse_list_block(tokens)  # parser already produces rows
  return [ItemType(**row) for row in rows]  # or DataFrame if preferred

  The egress is:

  for item in field_value:
      write_row(dataclasses.asdict(item))

  No fill-value logic, no sparse COO, no shape resolution, no dimension
  inference. The 700-line structure_array shrinks to something much smaller, and
   the _hack_period_non_numeric hack disappears entirely.

  ---
  Impact on codegen

  PR #310's lak.py would go from 561 lines to roughly 80. The codegen template
  no longer needs to emit __block_col_maps__, per-column array attrs,
  _set_block, _get_block, _packagedata, or __attrs_post_init__. This is the
  strongest argument for making this decision before that PR is merged — once
  the fan-out pattern is encoded into every generated package file, it's very
  expensive to undo.

  ---
  What about xattree?

  xattree currently tracks DataArrays with dimensional metadata. List fields
  wouldn't be DataArrays. There are two options:

  1. Store them as opaque attrs fields that xattree doesn't try to
  dimensionalize. The xarray view is explicitly computed when needed.
  2. Wait until xattree is replaced (the SDD calls it temporary; issue #282
  discusses moving to pydantic/dataclasses).

  Option 1 is the pragmatic near-term path. The point is that xarray's
  dimensional semantics are valuable for gridded arrays (IC strt, NPF k, CHD
  spatial views), but not for relational list structures (LAK packagedata).
  Maintaining the distinction is correct.

  ---
  Where to draw the line

  There are three genuinely different cases:

  Field type: Static list block
  Canonical example: LAK packagedata
  Natural Python type: list[ItemType]
  xarray role: optional view via .to_dataset()
  ────────────────────────────────────────
  Field type: Sparse period data
  Canonical example: CHD period
  Natural Python type: dict[int, list[ItemType]]
  xarray role: optional view materializing (nper, nodes)
  ────────────────────────────────────────
  Field type: Period flag / keystring
  Canonical example: OC period, STO period
  Natural Python type: dict[int, list[ItemType]]
  xarray role: not needed
  ────────────────────────────────────────
  Field type: Grid-aligned array
  Canonical example: IC strt, NPF k
  Natural Python type: NDArray + xattree
  xarray role: primary

  The fan-out was only ever relevant for the first two categories, and even
  there it's a view, not the truth.

  ---
  One concern worth flagging

  For very large stress packages (millions of active cells), a
  list[ChdPeriodItem] has more Python object overhead than a set of NumPy column
   arrays. The mitigation is to make ItemType a NamedTuple (cheaper than
  dataclass), or to allow constructing from a pd.DataFrame / np.recarray
  directly at the init boundary, converting internally. Since this is an IO
  concern, not a user API concern, it can be handled in the converter without
  surfacing in the class definition.

  ---
  Timing

  This decision needs to be made before PR #310 is merged. Once the codegen
  template encodes the fan-out and produces it for all ~200 MF6 packages, the
  migration cost jumps by an order of magnitude. The design is the right one;
  the moment to act is now.

  a case for using pd.DataFrame or np.recarray as the internal representation   
  instead of the list? I like the simplicity of the list and how it matches the 
   DFN, and it can represent non-tabular data too (where the item type is a

  field in period data). But DataFrame is the canonical way to store tabular    
  data in Python these days, no?                                                

⏺ Good question. My view: list[ItemType] is the right primary representation,
  and DataFrame is the right interface — accepted as input, returned as a view.
  The reasons:

  The uniformity argument wins. DataFrame can't cleanly represent union item
  types. OC period data rows have different schemas per arm (SAVE HEAD ALL vs
  PRINT HEAD STEPS 3 4); a DataFrame would need None/NaN for columns that don't
  apply to a given arm, which collapses the type information you're trying to
  preserve. If you use DataFrame for the tabular case and list for the union
  case, you now have two representations in codegen, two converter paths, and
  callers who have to know which case they're in. list[ItemType] — where
  ItemType is either a record dataclass or a union — covers both cases with the
  same pattern.

  The "canonical" argument applies to operations, not storage. DataFrame is
  canonical for analytical operations on tabular data — selection, groupby,
  merge, reshape. For storing a typed sequence of structured records, a typed
  Python list is actually the idiomatic 3.7+ choice. list[LakPackagedataItem] is
   statically checkable, easy to construct incrementally (append, list
  comprehension), easy to mutate (item.strt = 5.0), and readable in generated
  code. DataFrames are harder to construct row-by-row and mutation patterns
  (pd.concat, .loc) are awkward for the "modeler editing a few lake parameters"
  use case.

  DataFrame belongs at the boundary, not at the core. Accept it on construction
  (convert to list[ItemType] internally), provide it as a property for the
  tabular case:

  packagedata: Optional[list[LakPackagedataItem]] = field(...)

  @property
  def packagedata_df(self) -> pd.DataFrame | None:
      if self.packagedata is None: return None
      return pd.DataFrame([dataclasses.asdict(r) for r in self.packagedata])

  This is the same relationship xarray has with numpy: numpy is the storage,
  xarray is the view. DataFrame is the view for list-of-records; the list is the
   canonical form.

  The memory concern is smaller than it appears. For packagedata-style tables
  (LAK, SFR, MAW), row counts are typically hundreds to low thousands — well
  within Python object overhead tolerance, especially with NamedTuple or
  __slots__ dataclasses. For sparse stress period data (dict[int, 
  list[ChdPeriodItem]]), this representation is actually more memory-efficient
  than the current approach, which materializes a full (nper, nodes) dense array
   with fill values for every non-CHD cell. The concern only bites for extremely
   dense spatial coverage over many periods, exactly when the xarray view
  (computed on demand) is the right tool anyway.

  So: list[ItemType] primary, DataFrame accepted at init and exposed as a
  property for tabular cases. np.recarray I'd leave aside — it doesn't improve
  on either option and has a worse API than both.
