⏺ Your suspicion is correct — this is not lazy/streaming loading, and the
  developers' own profiling script admits as much.

  What .load(..., chunks=...) actually does (flopy4/mf6/package.py:211-284):
  1. Reads the entire file and parses it fully via the Lark grammar
  (codec.reader) into plain numpy arrays — this is 100% eager, same as before.
  2. Only after the package is fully built, if you passed chunks=, it goes back
  over the griddata/period fields and calls da.from_array() on the numpy arrays
  already sitting in memory, splitting them into per-layer dask blocks (lines
  246-282).

  So "chunked loading" doesn't reduce I/O, doesn't reduce peak memory during
  load, and doesn't defer any parsing — the full array exists in memory before
  it's ever wrapped in dask. The reader itself (flopy4/mf6/codec/reader/) has
  zero dask awareness (I grepped it — no hits at all).

  The docstring in docs/profile/chunked_profile.py says this outright:

  ▎ "Also profiles text-format load to confirm dask wrapping adds zero 
  ▎ overhead."
  ▎ "Load from text file (Lark parser dominates — confirms zero dask overhead)"

  And the test that's supposed to prove laziness,
  test_load_npf_lazy_no_compute_on_load (test/test_chunked.py:153), only asserts
  that wrapping a numpy array in da.from_array doesn't trigger .compute() —
  which is trivially true by construction and says nothing about whether the
  read was lazy.

  Where the dask work is real: the write path. array2chunks in
  flopy4/mf6/codec/writer/filters.py:71-114 genuinely streams — if a field is
  dask-backed (e.g. you constructed the package yourself with a dask array, not
  via .load()), the writer iterates .blocks and computes/writes one layer at a
  time, never materializing the whole array. array_how() (same file, lines
  18-50) explicitly avoids the value.max()==value.min() constant-check for dask
  arrays because that would force a full compute. Similarly
  to_xarray()/to_dataarray() (package.py:415-456) "stay lazy" if the field you
  handed them already holds a dask array — but you have to bring your own lazy
  array; the file loader doesn't produce one.

  Why it's in the xattree-decoupling PR: see issue #167, which is the actual
  rationale doc. xattree worked by stealing attrs fields into __dict__ and
  proxying them through an auto-built xarray.DataTree — implicit, eager, and
  (per the issue) "too magical." That architecture didn't leave room for a field
  to just be a dask array with to_xarray() called explicitly and lazily on
  demand. Decoupling to plain attrs classes removed that constraint — ArrayLike
  in _types.py is now literally NDArray | dask.Array, and xarray conversion
  became an explicit, opt-in method instead of something xattree did
  automatically. So the dask work isn't lazy loading; it's "now that fields are
  plain attributes, they're free to hold a dask array if you give them one, and
  downstream (to_xarray, write) will respect that."

  If you actually want lazy loading from disk, the reader would need real
  changes — e.g. dask.array.from_delayed per layer with a delayed function that
  seeks/reads only that layer's bytes, instead of Lark parsing the whole file
  upfront. Nothing in this PR does that; the chunks= param on .load() is closer
  to "give me the eagerly-loaded result pre-chunked for convenience" than
  "lazily load."

⏺ Grammar: confirmed basic, not typed. codec.reader.load() → loads()
  (flopy4/mf6/codec/reader/__init__.py:1-42) hardcodes BASIC_PARSER (basic.lark)
  + BasicTransformer. That produces an untyped {BLOCK_NAME: [rows]} dict — no
  field types, no dims, no dfn semantics at all. There's a separate
  get_typed_parser(name) in parser.py that loads per-DFN generated grammars from
  grammar/generated/*.lark, but nothing in the load path calls it — it's dead
  from load()'s perspective right now.

  All the "typing" happens after parsing, in _structure_codegen_v2
  (converter/ingress/structure.py:359): it walks the target class's attrs field
  metadata (dfn_block, schema, oc_action, aliases, inner-class keywords) and
  uses that to interpret the untyped rows — matching block names/keys to fields,
  coercing values, parsing packagedata/period recarrays, resolving griddata
  shapes from dims. So the class itself carries the schema; the grammar stays
  generic. That's presumably exactly the seam your PR is targeting.

  On making it generic over Component: mechanically easy but I don't think it
  buys much yet, and I'd hold off. Reasons:

  - Every class that's actually migrated to "codegen v2" (has dfn_block
  metadata) is already a Package subclass — Exchange, Solution, Tdis, all the
  model packages. They get this loader for free today.
  - Context/Model/Simulation are the only other Component branches, and they're
  not codegen v2 — still plain @xattree classes using the legacy _load = 
  IO(Loader) path, with their own recursive load() (Context.load,
  component.py:132) that also loads children via workspace-relative cd(). That's
  a different codec, different semantics (recursion), and _structure_codegen_v2
  has no idea how to parse a .nam file's packages/models/exchanges blocks
  anyway.
  - So relocating Package.load to Component.load right now would just rename
  where a Package-only special case lives — it wouldn't newly work for
  Model/Simulation, and it'd collide with the existing
  Component.load/Context.load methods (you'd need some dispatch: "does this
  class have dfn_block metadata → codegen-v2 path, else → legacy xattree path"),
  which is arguably worse than the current # type: ignore[override] on Package
  alone.

  I'd wait until your codec read-side PR settles what nested/hierarchical
  loading looks like for Model/Simulation, then lift the single-file loader up
  as part of that — otherwise this is speculative generalization for a shape we
  don't know yet. Want me to just do the chunks= removal on Package.load for now
  and leave the location alone?

⏺ Good, I pulled the PR. A few things worth flagging before answering the actual
  question.

  The recursive design is real, and I agree it's elegant. PR #284 doesn't
  recurse in Component.load()/Context.load() anymore — it strips that down to a
  single cls._load(path, format) call (component.py diff) and moves recursion
  into structuring itself: a namefile's packages/models/exchanges/solutiongroup
  blocks get parsed as typed binding records, and Binding.to_component() (new
  binding.py) looks the type string up in an FTYPES registry (ftype → class,
  populated automatically via __attrs_init_subclass__ just like the existing
  COMPONENTS registry) and calls component_cls.load(path) on it — which recurses
  naturally back through the same structuring pass for the child. So "load the
  tree" falls out of "load one file" + "one field type happens to be a reference
  to another file," rather than a special-cased for child in self.children: 
  child.load() loop bolted onto every container class. That's a good instinct —
  no objection to the shape.

  But there's a real problem: this PR predates the xattree-decoupling work by 27
  commits. Its base (7698c7a) is an ancestor of 5dceb3b, not a descendant. Its
  structure.py/converter/__init__.py still runs on the old xattree spec system —
  get_xatspec, xattree.has(cls), field metadata["xattree"]["kind"] == "dim",
  from xattree import Array — none of which exists in the current
  _structure_codegen_v2 (which is driven entirely by dfn_block/schema/oc_action
  attrs metadata, no xattree involvement in parsing at all). It hasn't been
  rebased since, so landing it means reconciling two structuring engines, not a
  routine merge. Worth knowing going in.

  Splitting "namefile support" into what's actually being asked:

  1. Grammar (typed .nam records instead of generic list) — cheap, and largely
  salvageable as-is. The
  packages_record/models_record/exchanges_record/solutiongroup_record rules PR
  #284 adds to gwf-nam.lark, sim-nam.lark, etc. come from the code generator
  (dfn2lark.py + grammar/templates/component.lark.jinja/macros.jinja), not from
  anything xattree-related. The generated grammars already exist on develop
  today (unused — load() still calls get_basic_parser(), never
  get_typed_parser()), so this piece doesn't conflict with the decoupling work.
  I'd estimate this is a day or so of effort, mostly porting/adapting the
  template diff.
  2. Binding resolution in structuring — moderate, needs a rewrite rather than a
  port. The design (an FTYPES registry, Binding.to_component() doing
  cls.load(path) recursively, a dims-propagating context so DIS-provided dims
  reach sibling packages automatically instead of requiring an explicit dims=
  kwarg) is sound and architecture-agnostic. But the actual row-sniffing code
  (_resolve_bindings_in_dict, the dict/tuple/list heuristics) is written against
  the old dict-of-DataArrays shape and would need to be reimplemented against
  _structure_codegen_v2's {BLOCK: [rows]} shape and dfn_block metadata. A few
  days, not weeks — the hard parts (grammar, registry, recursion pattern) are
  already solved by the PR, it's plumbing work to retarget it.
  3. The actual blocker: Model and Simulation aren't codegen v2 yet. They're
  still Context subclasses (plain @xattree, no dfn_block attrs fields) —
  packages get attached to them as implicit tree children (sim["gwf6"] = model),
  not as named, typed attrs fields the way Npf.k is a field on Npf.
  _structure_codegen_v2 has nothing to bind into on a Model/Simulation class
  today. Before namefile structuring can produce a real tree, Model/Simulation
  need the same codegen-v2 treatment Package got — DFN-driven attrs fields for
  their package/model slots. That's the same shape of work as the decoupling PR
  itself, just one level up, and it's the real critical path — the structuring
  logic changes are almost secondary to it.

  My read: this is worth doing, but I'd sequence it as (3) → (2) → (1), or at
  minimum land (3) first, since binding resolution has nothing to bind into
  until Model/Simulation are attrs-based. Want me to scope out what migrating
  Model/Simulation to codegen v2 would take, or is that already covered by other
  in-flight work?
