  1. Record binary version at sync time (not the ref)
  When sync(version="develop") runs, after installing the binary we already call
   _query_mf6_version() on it. Instead of writing "develop" to _contract.py,

⏺ Meson: vcs_tag()

  Meson has a first-class built-in for exactly this — cleaner than the CMake
  equivalent because it runs at build time rather than configure time, so it
  picks up the correct commit even if you configure once and build across
  multiple commits:

  # meson.build
  vcs_tag(
    command: ['git', 'describe', '--tags', '--long', '--always'],
    input:  'src/version.f90.in',
    output: 'version.f90',
    replace_string: '@VCS_TAG@',
    fallback: meson.project_version(),
  )

  ! src/version.f90.in
  character(len=*), parameter :: GIT_VERSION = "@VCS_TAG@"

  mf6 -v then emits 6.6.0-42-gabc1234 on develop builds and exactly
  6.6.0-0-g<sha> on release tags. vcs_tag() is idiomatic Meson — no custom
  scripts needed.

  ---
  Self-describing MF6

  It's ambitious, but the architecture is sound, and it actually dissolves the
  whole class of problems you're working around right now.

  The core idea: mf6 --dump-spec emits the complete input/output specification
  as machine-readable TOML (or JSON). flopy4 sync then becomes:

  mf6 --dump-spec | flopy4 generate-classes

  Version alignment is structurally guaranteed — the spec and the binary are the
   same artifact. No registry fetch, no commit hash cross-referencing, no
  develop pointer ambiguity. It also works offline, which matters in
  HPC/air-gapped environments where the current devtools approach hits the
  network.

  The implementation question in Fortran is how you store the spec data in the
  binary. Two realistic paths:

  Embedded at build time (simpler)
  A Meson custom_target converts the DFN files to a single TOML blob and
  generates a Fortran source file with it as a string constant. mf6 --dump-spec
  just writes that constant to stdout. Binary size goes up modestly — the DFN
  set is on the order of a few hundred KB uncompressed.

  dfn_embed = custom_target('embed_dfns',
    input:   dfn_files,
    output:  'dfn_embed.f90',
    command: [python, 'scripts/embed_dfns.py', '@INPUT@', '@OUTPUT@'],
  )

  Runtime serialization (more powerful)
  MF6 already maintains internal representations of its input spec — it reads
  and validates against them. If those internal structures can be serialized,
  --dump-spec reflects the live spec rather than a frozen build-time snapshot.
  This is more work but means spec output could vary by configuration (e.g. with
   optional features compiled in).

  The honest tradeoffs:

  The embedded approach is tractable and could be prototyped without touching
  MF6's core logic — it's essentially a build system change plus a new CLI flag.
   The runtime serialization approach requires MF6 to expose its internal spec
  model, which is a larger refactor but aligns with where things like
  OpenAPI-capable frameworks have ended up.

  The long-term vision this enables is compelling: flopy4 becomes a thin adapter
   over a self-describing simulator, and the whole DFN-sync pipeline either
  shrinks dramatically or disappears. Any simulator that can emit its own spec
  gets flopy4 support for free. That's a much cleaner interface boundary than
  the current "scrape DFNs from the source repo" approach.

  Worth raising with the MF6 team as a deliberate design direction — even if the
   timeline is long, it affects decisions being made now (like how much to
  invest in the devtools registry infrastructure vs. treating it as a temporary
  bridge).
