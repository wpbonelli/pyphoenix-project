⏺ Good question, and I think the answer is: partially unified conceptually, but
  not mechanically — and for good reason.

  The shared property

  Both are "a value defined in component X, referenced by field metadata in
  component Y." That's real, but it's about where the pointer lives, not what
  the pointer does. When you look at what the reference means in each case, the
  similarities end quickly:

  ┌───────────┬──────────────────────────────────┬──────────────────────────┐
  │           │       Dimension reference        │    FK/index reference    │
  ├───────────┼──────────────────────────────────┼──────────────────────────┤
  │ Target    │ scalar integer value             │ row identity in a list   │
  ├───────────┼──────────────────────────────────┼──────────────────────────┤
  │ Consumer  │ shape expression (constrains     │ column value (identifies │
  │           │ array bounds)                    │  a row)                  │
  ├───────────┼──────────────────────────────────┼──────────────────────────┤
  │ Resolved  │ once, at component init          │ per-row, at data access  │
  ├───────────┼──────────────────────────────────┼──────────────────────────┤
  │ Validated │ array can be sized               │ row exists in referenced │
  │           │                                  │  list                    │
  └───────────┴──────────────────────────────────┴──────────────────────────┘

  A unified mechanism would need a kind discriminator that branches into
  entirely different code paths on both sides. That's abstraction that obscures
  rather than clarifies. Keep them separate.

  ---
  Dimensions: yes, mark them explicitly

  Your instinct is right. The shape grammar already references dimension
  variables by name — nlay, nrow, ncpl, nja, etc. — but in v1 there's no
  declaration that a given scalar field IS a valid dimension target. That
  implicit contract should be made explicit in v2:

  class ScalarFieldV2(FieldV2):
      type: Literal["keyword", "integer", "double", "string", "path"]
      dimension: bool = False   # True → may appear in shape expressions
      index: bool = False       # True → 1-based, codec applies 0-based 
  conversion
      ...

  This does several useful things:
  - Shape expressions can be validated — a reference to a non-dimension field is
   an error, a typo gets caught at schema load time
  - Tooling knows which fields must be resolved before any array in the same (or
   related) component can be sized
  - Cross-component resolution logic has a well-defined set of candidates to
  search

  The fields that would get dimension=True are basically everything that appears
   in any shape expression across the corpus: nlay, nrow, ncol, nper, nodes,
  nja, nvert, ncpl, naux, and a handful of package-specific counters. These
  cluster strongly in dimensions blocks, though some live in options (e.g.,
  naux). The dimensions block name in v1 was a convention, not a constraint;
  dimension: bool makes the constraint explicit.

  maxbound would not get dimension=True — it's a formatting artifact being
  dropped from the schema, and it shouldn't appear in any v2 shape expression.

  ---
  FK references: already handled by the index design

  Most "FK" references in the corpus are within-component, cross-block (e.g.,
  packagedata.ifno → period.ifno in the same stress package). The
  ListFieldV2.key + ScalarFieldV2.index design covers those.

  Truly cross-component integer FK references are actually rare. The cellid case
   (an index into the grid's cell numbering) uses index=True and the grid is
  always a known context — no explicit FK declaration is needed beyond the flag.
   The utl-obs id/id2 cross-component reference is string-based (boundary
  names), handled by the UnionFieldV2 design, so index doesn't apply there.

  ---
  What would a DfnSpec-level cross-component FK index add?

  If you wanted to make cross-component FK relationships queryable (e.g., "which
   lists reference packagedata.ifno from outside the component?"), you could add
   a fk_edges: dict[str, list[str]] to DfnSpec analogous to the
  fixed_edges/free_edges for component relationships. But this feels premature —
   the corpus doesn't have enough cross-component integer FK cases to justify it
   now. The index=True flag on both sides is sufficient for the codec, and a
  graph can be derived from that if needed later.

  ---
  Summary recommendation

  - Add dimension: bool = False to ScalarFieldV2 — makes dimension targets
  explicit, enables shape validation, formalizes what has been an implicit
  contract.
  - Do not unify dimension and FK references mechanically — they're different
  relationships that happen to cross component boundaries.
  - Cross-component FK references at the DfnSpec level: defer; current corpus
  doesn't warrant it.

  Want to capture this in dfn_format_rules.md as a new section on the
  shape/dimension system, or is this better suited for dfn_refactor.md?
