Option 1: Format annotations as an optional sidecar on each field class               
                                                                                        
  Each pydantic field class gets an optional format: FieldFormat | None = None
  attribute. FieldFormat is itself a pydantic model:                                    
                                                            
  class FieldFormat(BaseModel):                                                         
      reader: Literal["urword", "readarray", "u1ddbl", "u2ddbl"] = "urword"
      tagged: bool = True                                                               
      preserve_case: bool = False
      layered: bool = False                                                             
                                                                                        
  class ScalarFieldV2(BaseFieldV2):
      type: Literal["keyword", "integer", "double", "string"]                           
      format: FieldFormat | None = None                                                 
  
  Structurally clean — format info is attached to the field but lives in a clearly      
  separated sub-object. The codec layer reads field.format; the schema layer reads
  everything else. Cost: format info is still co-located with the structural schema,    
  just nested one level deeper. If you want to load a spec purely structurally (ignoring
   format), you have to remember to ignore format.

  ---
  Option 2: Parallel FormatSpec alongside DfnSpec
                                                                                        
  Format info lives in a completely separate object, parallel to the structural spec:
                                                                                        
  class FieldFormat(BaseModel):                             
      reader: str = "urword"                                                            
      tagged: bool = True                                   
      preserve_case: bool = False                                                       
      layered: bool = False                                 

  class BlockFormat(BaseModel):
      fields: dict[str, FieldFormat] = {}
                                                                                        
  class ComponentFormat(BaseModel):
      name: str                                                                         
      blocks: dict[str, BlockFormat] = {}                   

  class FormatSpec(BaseModel):                                                          
      components: dict[str, ComponentFormat]
                                                                                        
  The codec receives both DfnSpec (structure) and FormatSpec (format), indexed by the   
  same component/field names. For the period recarray case specifically, BlockFormat
  could carry input_style: Literal["list", "readarray", "keyword-value"] at the block   
  level rather than per-field, since that's where the convention really lives.

  Cleanest separation — structural and format specs are fully independent objects. Cost:
   two objects to load, maintain, and keep in sync. Field identity (the key linking
  them) needs to be consistent.                                                         
                                                            
  ---
  Option 3: Format as a block-level annotation, not field-level
                                                               
  MF6's format conventions are largely block-scoped: a period block is always a sparse
  list, an options block is always keyword-value pairs, an array block uses READARRAY.  
  Field-level format attributes (reader, tagged) fall out from this block-level
  convention in most cases. So the format layer could be:                               
                                                            
  class BlockInputStyle(BaseModel):
      kind: Literal["keyword-value", "list", "readarray"]
      # list: sparse recarray, one row per cell — period blocks                         
      # readarray: READARRAY control line — array blocks                                
      # keyword-value: standard options/dimensions blocks                               
                                                                                        
  class ComponentFormat(BaseModel):                                                     
      name: str                                             
      blocks: dict[str, BlockInputStyle]
                                                                                        
  This is coarser than per-field format info but probably sufficient for most codec     
  decisions, and maps cleanly onto the structural transform (map_period_block is a      
  consequence of kind="list" on a period block). Individual field-level quirks          
  (preserve_case, tagged) could be exceptions layered on top if needed.

  ---
  My recommendation: Option 2 or 3 depending on how fine-grained the codec decisions
  need to be. Option 3 is the most principled — it recognizes that format conventions in
   MF6 are block-scoped, not field-scoped — and it maps directly onto the period        
  recarray case. Option 1 is worth avoiding because it keeps format info structurally   
  adjacent to the schema even if logically separated.                                
                                                     
  Worth noting: the TOML files that dfn2toml.py generates could carry both the
  structural spec and the format annotations (as separate TOML tables), so format info  
  doesn't have to live in a separate file — just a separate section.
